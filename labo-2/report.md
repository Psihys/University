## Test Cases

### TC-LOGIN-01 — Успішна авторизація standard_user

* **Type:** Positive
* **Preconditions:**
  * Відкрита сторінка Login SauceDemo.
  * Користувач не авторизований.
* **Test Data:**
  * Username: `standard_user`
  * Password: `secret_sauce`
* **Steps:**
  1. У поле Username ввести `standard_user`.
  2. У поле Password ввести `secret_sauce`.
  3. Натиснути кнопку Login.
* **Expected Result:** Після введення `standard_user` і правильного пароля та натискання Login користувач успішно авторизується і переходить на сторінку Products (`/inventory.html`).
* **Actual Result:** Після введення `standard_user` і правильного пароля та натискання Login відкрилася сторінка Products.
* **Result:** Pass

* **Type:** Negative
* **Preconditions:**
  * Відкрита сторінка Login SauceDemo.
  * Користувач не авторизований.
* **Test Data:**
  * Username: `standard_user`
  * Password: `wrong_password`
* **Steps:**
  1. У поле Username ввести `standard_user`.
  2. У поле Password ввести `wrong_password`.

* **Actual Result:** Після введення `standard_user` та неправильного пароля з'явилося повідомлення про помилку: *"Epic sadface: Username and password do not match any user in this service"*.

## Контрольні питання

1. **Що таке Test Basis і навіщо він потрібний?**  
   *Test Basis* — це сукупність вимог, специфікацій або опису системи, на основі яких розробляються тести. Він необхідний для визначення умов тестування та формування очікуваного результату (Expected Result).

2. **Чим Test Condition відрізняється від Test Case?**  
   *Test Condition* відповідає на питання «Що саме перевірити?» (високорівнева ідея/подія), а *Test Case* — на питання «Як це перевірити?» (містить конкретні кроки, входні дані, передумови та очікуваний результат).

3. **На яке питання відповідає Test Analysis?**  
   Test Analysis відповідає на питання: **«Що тестувати?»** (визначення умов тестування на основі аналізу вимог).

4. **На яке питання відповідає Test Design?**  
   Test Design відповідає на питання: **«Як тестувати?»** (створення та деталізація тест-кейсів, підбір тестових даних).

5. **Для чого використовується checklist?**  
   Чекліст використовується для швидкої та зручної фіксації переліку перевірок без витрати часу на детальний опис кожного кроку.

6. **Чому checklist не завжди може замінити детальний test case?**  
   Чекліст не містить детальних кроків та точних тестових даних, тому інший тестувальник або новий член команди може виконати тест некоректно чи зрозуміти очікуваний результат по-різному.

7. **Чим positive test відрізняється від negative test?**  
   *Positive test* перевіряє, чи працює система згідно з вимогами при введенні валідних даних. *Negative test* перевіряє, чи коректно система обробляє невалідні або помилкові дані та чи відображає відповідні повідомлення.

8. **Чому negative test може мати результат Pass?**  
   Тому що для негативного тесту очікуваним результатом є успішне відхилення некоректних даних системою. Якщо система правильно відхилила вхід і показала помилку — тест вважається пройденим (Pass).

9. **Для чого використовується Decision Table?**  
   *Decision Table* використовується для аналізу та систематизації складних комбінацій вхідних умов і бізнес-правил, щоб гарантувати відсутність пропущених сценаріїв.

10. **Навіщо порівнювати Expected Result та Actual Result?**  
    Порівняння необхідне для об'єктивного встановлення відповідності між реальною поведінкою системи та вимогами, а також для виявлення та фіксації дефектів (аномалій).

11. **Що означають Pass та Fail?**  
    *Pass* — фактичний результат (Actual Result) повністю відповідає очікуваному (Expected Result).  
    *Fail* — фактичний результат відрізняється від очікуваного (виявлено помилку/дефект).
